# Architecture and transport decision

This is a one-host/one-viewer SDR prototype. The host opens a local movie, decodes it with FFmpeg, scales video to at most 1920×1080, encodes H.264 constrained baseline without B frames, and encodes stereo 48kHz Opus. The standalone viewer decodes both streams and renders with SDL2. No HTTP movie endpoint, movie DataChannel transfer, muxer, or viewer movie writer exists.

## Control plane

Appwrite Functions are request handlers, not persistent WebSocket servers. A verified Appwrite Account JWT identifies the caller. Private database documents hold rooms, membership sessions, host-authorized connection generations, and immutable SDP/ICE inbox messages. Recipient-only Realtime notification documents contain a room identifier, expiry and SHA-256 delivery receipt, **not SDP, ICE credentials, or media**. The native client authenticates an Appwrite Realtime WebSocket using a session secret and subscribes using the current official SDK protocol. It treats notifications as wake-up hints and always fetches the inbox through the Function.

Two-second polling is the recovery path for missed notifications, older Realtime protocols, and JWT-only clients. HTTP runs on a worker so Function latency cannot block media pacing/rendering. Heartbeats run every ten seconds; membership leases last 120 seconds. The client pauses playback and closes media at 100 seconds without a successful heartbeat, before the 120-second membership lease expires. It retries coordination for five minutes, rejoins an expired lease, and creates a fresh connection generation. A replaced session or revoked JWT stops immediately. Expiry, closure, leave, and session rotation revoke future signaling. An already established P2P connection requires the applications to enforce revocation: host room checks run every two seconds; session replacement is included in the host's room snapshot. The backend cannot revoke an SRTP connection remotely without cooperating clients.

Every mutating transaction stages a room revision write and re-reads that staged room **before** authorizing. This matters because a preliminary Appwrite read is not a database lock. Membership, peer state, queue deletion, and signaling changes commit together; conflicting commits retry four times. Room capacity is two members. Signaling is limited to 180 messages/minute/member and 64 queued messages/room, with 120-second expiry. Polling also authorizes transactionally. Schedule cleanup to remove expired signals/receipts and retained closed rooms. Private per-user counters also limit creation and invitation attempts. Room snapshots now include the authoritative connection generation; delayed offers cannot replace it.

Native signaling uses a bounded 256-entry delivery ledger with five-minute deduplication and retry backoff. Fetching is separate from processing and ACK. Outgoing requests retain IDs across transient failures; server receipts remain valid after ACK deletion. Authorization requests retain their own IDs, and incoming candidates are retried until remote SDP exists. SDP and candidate application are themselves idempotent within a connection. Signaling event/outbound queues have hard bounds; overload fails closed rather than silently growing memory. Closing a peer drains external media/control callbacks before playback targets can be released.

## libdatachannel vs libwebrtc

| Area | libdatachannel 0.24.1 | libwebrtc |
| --- | --- | --- |
| C++20/CMake integration | Small standalone library with encoded-media tracks | Large Chromium/GN toolchain and unstable integration surface |
| Custom FFmpeg encoding | Direct encoded-frame/RTP handler integration | Requires custom encoder/decoder integration with libwebrtc media engine |
| Encryption and connectivity | ICE, DTLS fingerprint verification, SRTP/SRTCP, SCTP | Full WebRTC stack |
| Feedback | RTCP SR/RR, NACK responder, PLI, REMB helpers | Integrated feedback, jitter recovery and bandwidth estimation |
| Congestion control | Application must supply media rate control and pacing | Mature integrated controller, including delay-based estimation |

**Chosen for this prototype: libdatachannel**, with explicit bounded RTP pacing, receiver sequence reordering, NACK requests, PLI recovery, RR and REMB feedback, and a conservative loss/jitter-based bitrate controller. This is real media transport, not video over a reliable DataChannel. Libwebrtc remains the stronger production choice if Internet congestion tests show this controller insufficient. This prototype does not implement Google's GCC or transport-wide congestion control and does not promise production behavior under arbitrary Internet bottlenecks.

The pinned default libjuice backend supports one STUN server and up to two **UDP TURN** servers. TCP/TLS TURN configurations are rejected rather than silently ignored. Networks blocking UDP require a different ICE backend (such as libnice) or libwebrtc; this build does not solve that case. TURN credentials are supplied at runtime, never embedded. `PARTY_RELAY_ONLY=1` requires configured TURN.

## Media and clocks

- Host demux/decode/encode are separate from signaling and from `Peer`. File reading stays host-side.
- FFmpeg tries NVENC, QSV and AMF if compiled in and usable at encoder open, then libx264. Software encoding is explicitly selectable. Vendor failures later during encoding are reported; runtime migration between GPU vendors is not implemented.
- H.264 RFC6184 packetization uses a 90kHz RTP clock; Opus uses 48kHz. Both come from one continuous host steady-clock transport timeline. Seek/control transitions clear unsent video pacing packets and request an IDR; intentional epoch discards have a separate counter from congestion drops. RTCP sender reports are generated by libdatachannel.
- Movie position and transport timestamps are distinct. Seeking flushes input decoders, resets resampling/FIFO state, recreates encoders, establishes a future transport cutoff, and sends an IDR. RTP sequence numbers/timestamps do not jump backwards within a connection.
- An ordered encrypted control DataChannel carries host state and NTP-style ping/pong clock samples. It never carries movie bytes. Viewer play/pause/seek commands are ignored by the host.
- The receiver extends sequence numbers across 16-bit wrap, waits 60–250ms for missing packets, using bounded SCTP RTT as a retry-window estimate, NACKs gaps, bounds reordering to 512 packets, and discards incomplete H.264 access units. Keyframe requests are throttled. Receiver cutoff changes clear partial access units and reject packets from previous playback epochs before sequence/loss accounting. Missing clock anchors do not influence jitter estimates.
- Receiver compressed queues are bounded to 8MiB; video access units to 4MiB; decoded video to 15 frames; decoded audio to 50 Opus packets; sender pacing to 512KiB. Buffers hold only a short live window.
- The viewer uses a 350ms playout delay. Its SDL audio queue is the master for video scheduling. The NTP estimator renews its best-RTT window every 30 seconds and resets on peer replacement. Offset correction after initialization is bounded to 5ms per accepted sample. Minor clock drift changes audio resampling by at most 0.5%; late video is dropped and early video held. Large gaps rebuffer. Startup/rebuffer trims old audio to the live playout target so an audio clock delayed by an IDR/output stall cannot permanently outlive the bounded video queue. Clock lag over 250ms reanchors buffered playback; small drift still uses gradual correction. New epochs clear stale queued media and wait for a decodable IDR. Pause freezes video and clears queued audio.
- `--preview` routes the same encoded stream into a local host `Player`, with the same playout delay, so the host can watch alongside the viewer. Remote clock skew/network delay can still affect alignment; cross-machine audiovisual calibration remains required.

## Statistics and limits

Statistics include ICE/connection state, candidate types, SCTP RTT, RTP receive/loss/NACK counters, jitter, bitrate target, pacing queue/drops, decoder counts, audio energy, decoded luma checksum, queue sizes, rebufferings and A/V scheduling drift. Peer byte counters are labeled **DataChannel** bytes; media video bytes are counted separately by the pacer. Test resource figures cover the combined host/viewer process, not separate machines.

The video sender changes bitrate by reopening the encoder at most once per five seconds, with repeated SPS/PPS and IDR recovery. Resolution does not adapt to sustained low bandwidth. Audio packet gaps up to 100ms are concealed with silence; Opus in-band FEC is enabled in the encoder but the receiver does not invoke FEC/PLC explicitly. The receiver jitter buffer is fixed, not a production adaptive NetEQ implementation. Audio/video streams with no usable input timestamps are rejected. Both video and audio are required. HDR PQ/HLG inputs are rejected because tone mapping is not implemented. Subtitles, multiviewer fan-out, surround audio, 4K/HDR/Dolby Vision, long-duration drift tests, and integration with the user's main player are future work.
